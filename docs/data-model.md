# Data Model

This is a **proposed analytical model**, not an implemented Power BI model.
It is based on the actual [profiling and relationship validation report](../data/processed/data-profile.json)
generated by [profile_data.py](../scripts/data-cleaning/profile_data.py).
Column descriptions and null rates are recorded in the [data dictionary](data-dictionary.md).
All preparation steps below are proposals for later implementation. No data has
been cleaned, removed, or transformed for this model, and no Power BI files have
been created.

The first six relationships have no null foreign-key rows and no unmatched keys.

| products.product_category_name | product_category_name_translation.product_category_name | 32,951 | 73 | 71 | 2 | 97.2603% |

Products contain **610 rows with null category values**, excluded from the
category match denominator. The two unmatched distinct category values are
`pc_gamer` and `portateis_cozinha_e_preparadores_de_alimentos`. Two unmatched
values does not mean two product rows; affected row counts were not reported
by this relationship check.

All expected parent keys are unique and non-null in the current data:

| Source parent | Validated key | Rows / distinct keys |
| --- | --- | ---: |
| customers | customer_id | 99,441 |
| orders | order_id | 99,441 |
| products | product_id | 32,951 |
| sellers | seller_id | 3,095 |
| product_category_name_translation | product_category_name | 71 |

These checks establish child-to-parent coverage, not that every order has an
item, payment, or review. The three child tables cover different sets of orders.
In particular, FactSales would cover 98,666 orders, not all 99,441 source orders.
The profile also finds customer_id unique in orders, but order_id remains the
proposed order lookup key. Observed uniqueness is not a future guarantee.

## Proposed fact tables and grains

Use three separate fact tables with shared customer and date dimensions.
Preserve every source fact row. Proposed primary keys below are logical row
identifiers supported by the observed candidate-key results; they are not
implemented constraints.

| Table | Grain | Main source in data/raw/ | Expected rows before any later filtering | Proposed logical primary key |
| --- | --- | --- | ---: | --- |
| FactSales | One order-item record within an order | olist_order_items_dataset.csv | 112,650 | (order_id, order_item_id) |
| FactPayments | One payment-sequence record within an order; not one row per installment | olist_order_payments_dataset.csv | 103,886 | (order_id, payment_sequential) |
| FactReviews | One review/order pair; neither one row per order nor one row per review_id alone | olist_order_reviews_dataset.csv | 99,224 | (review_id, order_id) |

All three would use `olist_orders_dataset.csv` as an additional preparation
lookup on its unique `order_id`, bringing in `customer_id`, purchase timestamp,
and relevant order attributes. A left lookup from each fact source should
preserve its row count; validate that during implementation. This is an
enrichment proposal, not a join already performed.

| Table | Proposed dimension foreign keys | Retained source fields / measure inputs |
| --- | --- | --- |
| FactSales | customer_id -> DimCustomer; product_id -> DimProduct; seller_id -> DimSeller; OrderDate -> DimDate.Date | order_id, order_item_id, price, freight_value, shipping_limit_date; order status and relevant order timestamps from orders |
| FactPayments | customer_id -> DimCustomer; OrderDate -> DimDate.Date | order_id, payment_sequential, payment_type, payment_installments, payment_value |
| FactReviews | customer_id -> DimCustomer; OrderDate -> DimDate.Date; optional inactive ReviewCreationDate and ReviewAnswerDate -> DimDate.Date | review_id, order_id, review_score, review text, review_creation_date, review_answer_timestamp |

`OrderDate` would be the date portion of `order_purchase_timestamp` obtained
from orders. Review date keys would similarly be derived during preparation.
The payment source has no payment timestamp: an OrderDate filter on
FactPayments describes the purchase-date cohort, not the date cash was received.

Retain `order_id` in each fact for traceability and distinct-order measures;
it references orders in the source/preparation layer. The base proposal does
not create relationships between the facts on this non-unique field or add
an Orders table to the loaded semantic model. Whole-population order counts
or a shared order slicer would require a separately designed order dimension
or order-grain fact later, including a review of filter paths.

The review profile also finds `(order_id, review_answer_timestamp)` unique.
Prefer `(review_id, order_id)` as the proposed logical identity and validate
its continued uniqueness on refresh. Do not drop repeated review_id or order_id
values to force an unsupported single-column key. Composite fact keys identify
rows; dimension relationships below use single-column dimension keys.

## Proposed dimensions

| Dimension | Grain and proposed primary key | Source | Proposed attributes / scope |
| --- | --- | --- | --- |
| DimCustomer | One source customer_id; PK customer_id (99,441 observed rows) | olist_customers_dataset.csv | customer_unique_id, postal-code prefix, city, state |
| DimProduct | One product_id; PK product_id (32,951 observed rows) | olist_products_dataset.csv, enriched from product_category_name_translation.csv | Original category, English category where available, product measurements and descriptive metadata |
| DimSeller | One seller_id; PK seller_id (3,095 observed rows) | olist_sellers_dataset.csv | Postal-code prefix, city, state |
| DimDate | One calendar day; PK Date | Generated calendar based on the date roles selected from orders, items, and reviews | Year, quarter, month number/name, day; continuous dates over the required range |

DimCustomer preserves the validated customer_id grain. `customer_unique_id`
is not a detected single-column key and must not be used as the relationship's
one-side key without additional identity analysis. A count of DimCustomer rows
therefore means source customer identifiers, not a validated count of people.

For DimProduct, propose a left lookup to the translation table using
`product_category_name`, whose parent key is unique. Preserve all products,
their original category values, and missing translations. Any display label
for unknown categories should be decided in the later preparation phase;
this proposal does not invent translations or remove unmatched categories.
The translation table would supply attributes rather than a separate loaded
dimension in this initial design.

DimDate would be a dedicated date table. Choose the calendar boundaries after
checking actual minimum/maximum dates; the current profile does not report
those ranges. Keep source timestamps for time-of-day and duration analysis.
Additional shipping, approval, delivery, and review date roles can use inactive
relationships with explicit measures, or separate role-playing date dimensions
if simultaneous date-role filtering becomes a requirement. Missing timestamps
must remain visible as missing; do not fabricate dates.

Geolocation is excluded from the initial loaded model. Its 1,000,163 rows
include 261,831 exact duplicate rows, and the profiler found no single-column
or two-column candidate key. A direct postal-prefix lookup could multiply
dimension rows. Geographic enrichment needs a separate grain and aggregation
decision before implementation; no geolocation records are cleaned here.

## Proposed Power BI relationships

Use one-to-many relationships with single-direction filtering from dimensions
to facts. Customer and date filters can apply to all three facts; product and
seller filters apply only to FactSales in this proposal.

| One side | Many side | Proposed state |
| --- | --- | --- |
| DimCustomer.customer_id | FactSales.customer_id | Active |
| DimCustomer.customer_id | FactPayments.customer_id | Active |
| DimCustomer.customer_id | FactReviews.customer_id | Active |
| DimProduct.product_id | FactSales.product_id | Active |
| DimSeller.seller_id | FactSales.seller_id | Active |
| DimDate.Date | FactSales.OrderDate | Active |
| DimDate.Date | FactPayments.OrderDate | Active |
| DimDate.Date | FactReviews.OrderDate | Active |
| DimDate.Date | FactReviews.ReviewCreationDate | Optional, inactive |
| DimDate.Date | FactReviews.ReviewAnswerDate | Optional, inactive |

The active date relationships deliberately align comparisons on purchase date.
Measures using a review event date would explicitly select that date role.
The validated source relationships support this design, but derived customer
and date foreign keys still need validation after future preparation.

## Why facts must remain separate

Order Items has **112,650 rows across 98,666 orders**, Payments has **103,886
rows across 99,440 orders**, and Reviews has **99,224 rows across 98,673 orders**.
The repeated order_id values represent different grains. Joining raw payments
or reviews directly to order items on order_id would multiply rows and could
duplicate sales amounts, payment amounts, and review counts or weight scores
by the number of items/payment records.

For illustration only, an order with three items, two payment records, and
two review records would produce twelve rows if all three tables were joined
on order_id. Each item would appear four times, and each payment or review
would appear six times. This example explains the risk; it is not an observed
order from the profile.

Propose explicit measures evaluated in their own facts: sum item price and
freight in FactSales, sum payment_value in FactPayments, and count review rows
or average review_score in FactReviews. These are measure inputs, not yet
approved revenue definitions; order-status rules, currency, and the meaning
of sales versus collected payments require business validation. Review-row
counts and distinct reviewed-order counts should be named separately.

Do not attribute payment amounts or reviews to individual products or sellers
through a direct fact-to-fact relationship. Such analysis needs an explicit
allocation or order-selection rule. Until defined, payment and review measures
should not be presented as product- or seller-level results, since those
dimension filters do not filter those facts in this design.

## Validation before future implementation

Recheck source keys on refresh, preserve fact row counts through order lookups,
and verify all proposed dimension keys and derived foreign keys. Reconcile
measure totals against their source facts independently, retain missing category
and date values for review, and verify date-role behavior. These checks and any
subsequent transformations remain future work; this document changes only the
proposed design.
